## 新同事拆分建议

拆分原则：按用户可感知结果拆，不按文件列表拆。

### 同事 A：文字聊天与设置体验产品化

目标：让普通用户能完成一条完整的文字对话：打开设置、看懂模型是否可用、输入文字、看到回复、必要时停止回复，并且桌宠气泡表现稳定。

为什么独立：

这条线只负责“用户怎么输入、怎么看到输出、怎么知道模型能不能用”。它不需要碰语音、记忆存储、桌面控制，也不需要改底层 provider 调度逻辑，适合独立推进。

做什么：

1. 设置页明确显示当前模型连接状态：
   - 缺 Base URL 时显示“需要填写服务地址”；
   - 缺 API Key 时显示“需要填写 API Key”；
   - 缺模型名时显示“需要选择或填写模型”；
   - 配置完整时显示“可以测试连接”。
2. Test LLM 按钮行为明确：
   - 当前有回复生成时，不能并发测试；
   - 页面要告诉用户先停止当前回复，或等待回复结束。
3. Chat 窗口完成基础文字链路：
   - 用户能输入一段文字并发送；
   - 用户消息进入聊天记录；
   - AI 回复能逐步显示；
   - Stop 能中断正在生成的回复；
   - 失败时显示明确错误，不静默无响应。
4. 桌宠消息气泡只承担“最近一条回复提示”：
   - 气泡不跟随拖拽持续移动，避免画面太躁；
   - 长回复在桌宠气泡里截断展示；
   - 完整回复保留在 Chat 窗口。
5. 保证设置页、聊天页、桌宠气泡三处状态一致：
   - 同一次回复不能出现 Chat 已停止但气泡还在继续更新；
   - 连接失败不能显示成“正在回复”。

不做什么：

- 不做语音朗读；
- 不做语音输入；
- 不做长期记忆策略；
- 不做多角色切换；
- 不改 provider 协议，只消费已有 runtime 状态；
- 不做桌面控制、浏览器控制、屏幕读取、长期任务、多智能体、插件市场、直播、VRM/Godot。

交付物：

- 一套用户能看懂的 Settings 状态面板；
- 一套可完成输入、回复、停止、错误展示的 Chat 体验；
- 桌宠气泡展示规则定稿：短句展示、长句截断、不跟随拖拽连续移动；
- 对应的产品验收说明：每个状态用户会看到什么、按钮是否可点、错误如何出现。

验收标准：

- 新用户不看文档，也能判断当前为什么不能测试模型；
- 配置完整后，用户能从设置页完成一次 Test LLM；
- 用户能在 Chat 发出一句话，并看到 AI 回复；
- 用户点击 Stop 后，回复停止，界面不再继续追加同一条内容；
- 长回复不会把桌宠气泡撑爆，完整内容仍能在 Chat 里看到；
- 拖动桌宠时，消息气泡不会持续跟着抖动或抢注意力；
- 模型错误、网络错误、配置错误都有可见反馈。

依赖/风险：

- 依赖现有 runtime 已经能发起 provider 请求、流式返回、Stop 中断；
- 风险是 UI 状态和 runtime 状态不同步，导致用户看到“能点”但实际不能用；
- 风险是气泡展示和 Chat 展示职责混在一起，导致桌宠界面越来越像网页聊天框。

建议工作树：

`codex/v1-chat-settings-polish`

### 同事 B：语音输出最小闭环

目标：让桌宠在收到 AI 文字回复后，能把回复用语音读出来，并且用户能清楚地开关、停止和理解当前语音状态。

为什么独立：

语音输出是另一条用户可感知链路：文字回复已经存在，语音只需要消费最终回复或分段回复，不应该反过来影响文字聊天主流程。它可以独立验收：即使语音失败，文字聊天仍然可用。

做什么：

1. 增加 V1 最小语音输出开关：
   - 用户能在设置里打开或关闭“AI 回复朗读”；
   - 默认策略要明确，建议默认关闭，避免突然出声。
2. AI 回复完成后触发朗读：
   - 短回复可以完整读出；
   - 长回复要有明确截断或分段策略，不能无限读。
3. 提供停止语音的用户动作：
   - 用户点击 Stop 时，正在生成的文字回复停止，正在播放的语音也停止；
   - 如果文字已完成但语音还在播放，也要能停止语音。
4. 展示语音状态：
   - 当前正在朗读时，用户能看到“正在朗读”；
   - 语音不可用时，用户能看到“语音不可用”或“未配置语音”。
5. 失败不阻塞文字：
   - TTS 失败时，Chat 文字回复仍保留；
   - 错误提示只说明语音失败，不把整次对话标成失败。

不做什么：

- 不做语音输入；
- 不做实时打断式口语对话；
- 不做情绪语音、复杂音色市场、声音克隆；
- 不做多角色声线系统；
- 不做口型同步精调，V1 只要求“有声输出可控”；
- 不做桌面控制、浏览器控制、屏幕读取、长期任务、多智能体、插件市场、直播、VRM/Godot。

交付物：

- 一个明确的语音开关；
- 一条“AI 文字回复 -> 语音朗读”的最小链路；
- 一个停止朗读的用户动作；
- 可见的语音状态与失败提示；
- 一份 V1 语音边界说明：读什么、不读什么、失败时怎么表现。

验收标准：

- 用户关闭语音后，AI 回复只显示文字，不出声；
- 用户打开语音后，AI 回复完成后会朗读；
- 用户点击 Stop 后，正在朗读的声音停止；
- 语音失败时，文字回复不丢失；
- 长回复不会造成不可控的长时间朗读；
- 用户能从界面判断当前语音是关闭、朗读中，还是不可用；
- 没有语音配置时，产品不会假装语音可用。

依赖/风险：

- 依赖同事 A 提供稳定的文字回复完成状态；
- 依赖 runtime 能区分“正在生成文字”和“正在播放语音”；
- 风险是语音播放和文字生成耦合太紧，导致 TTS 失败影响聊天；
- 风险是 Stop 只停文字不停声音，造成用户感觉失控；
- 风险是默认自动出声打扰用户，所以默认开关必须谨慎。

建议工作树：

`codex/v1-voice-output-loop`

两人协作口径：

- 同事 A 负责“用户输入文字、看到文字回复、看懂设置状态”；
- 同事 B 负责“已有文字回复如何变成可控语音输出”；
- 两边共享同一个原则：文字聊天是 V1 主链路，语音是附加输出；任何语音失败都不能破坏文字聊天；
- A 不需要为语音做复杂 UI，B 也不重新实现 Chat 或 provider 请求。
